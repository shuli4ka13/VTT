# VTT: модули — спецификация

Nov 20, 2026 · @Aliaksandr Latyshonak

## Кратко

Модуль — пакет данных и ассетов от стороннего автора, который мастер включает в комнате, а у игроков он подгружается сам. Первая версия — только данные (JSON, Lottie, картинки, звуки), без исполняемого кода: так безопасно, детерминизм движка не страдает, и модули проходят правила App Store и Google Play.

**Путь модуля**

1. Автор собирает модуль в мастерской (веб): манифест, данные, ассеты, настройки; проверяет в песочнице.
2. Публикует в каталог; модуль проходит проверку схемой и модерацию (ИИ плюс человек).
3. Мастер включает модуль в комнате (или автор — в системе, или игрок — для себя) и настраивает.
4. Сервер запоминает включённые модули и их версии; клиенты при входе в комнату скачивают нужное с CDN и кэшируют.
5. Эффект ссылается на анимацию из модуля; сервер рассылает событие, у всех проигрывается одно и то же.

**Входит в первую версию:** анимации эффектов, скины кубов, оформление фишек, иконки счётчиков, виджеты ресурсов стола, контентные пакеты (предметы, эффекты, раскладки листа), настройки модулей, мастерская, каталог.

**Не входит:** модули с кодом (свои виды отрисовки, новая логика правил). Если понадобятся — отдельным этапом с песочницей; в iOS-приложение их, скорее всего, не пустят.

Зависит от раздела «Стол: как делаем» в задачах по UX: анимации и оверлеи рисуются на canvas-слое Skia.

## Понятия

- **Модуль** — пакет: манифест `module.json` + данные + ассеты. Идентификатор вида `автор/имя`, версия по semver.
- **Точка подключения** — место в ядре, которое принимает модули определённого типа, со своим контрактом (какие данные нужны, что ядро с ними делает). Реализуется той же реестровой идиомой, что типы шагов в движке и виды слотов во фронте.
- **Ассет** — файл модуля: Lottie (JSON), PNG/WebP, SVG, звук (OGG/MP3).
- **Включение** — запись «где, какой модуль, какой версии, с какими настройками».

**Уровни включения**

| Уровень | Кто включает | Действует для | Пример |
| --- | --- | --- | --- |
| Система | автор системы | всех, кто играет по системе | пак анимаций, входящий в Daggerheart |
| Комната | мастер | всех за этим столом | анимации заклинаний, черепочки для Страха |
| Личный | игрок | только себя, видят и другие | скин кубов, рамка своей фишки |

Личные модули — только косметика своего: свои кубы, своя фишка. Они не меняют то, что видят другие на чужих фишках и в общих виджетах.

**Версии**

- Включение закрепляет версию. Обновление модуля не применяется само: мастер (автор системы, игрок) обновляет явно.
- Манифест указывает совместимость с версией ядра и с системой (для контентных пакетов). Несовместимый модуль не включается, а у уже включённого показывается предупреждение.
- Опубликованную версию нельзя изменить, только выпустить новую.

## Манифест

Zod-схема манифеста живёт в `packages/schema` рядом со схемой мира; по ней проверяются модуль в мастерской, при публикации и на клиенте при загрузке.

| Поле | Обязательно | Что это |
| --- | --- | --- |
| `id` | да | `автор/имя`, латиница, цифры, дефис |
| `version` | да | semver |
| `name`, `description` | да | подписи с переводами: `{ "ru": …, "en": … }` |
| `core` | да | диапазон совместимых версий ядра |
| `system` | нет | id и диапазон версий системы — для контентных пакетов |
| `levels` | да | на каких уровнях можно включать: `system`, `room`, `personal` |
| `requires` | нет | другие модули и их версии |
| `provides` | да | что модуль даёт: список подключений по точкам (см. ниже) |
| `settings` | нет | описание настроек (см. «Настройки модулей») |
| `assets` | да, если есть файлы | список файлов с типом и размером |
| `license` | да | лицензия контента |

**Пример**

```json
{
  "id": "ashwood/skull-fear",
  "version": "1.2.0",
  "name": { "ru": "Черепа Страха", "en": "Skulls of Fear" },
  "description": { "ru": "Страх ведущего черепами", "en": "GM Fear as skulls" },
  "core": ">=1.0 <2.0",
  "levels": ["system", "room"],
  "license": "CC-BY-4.0",
  "assets": [
    { "path": "skull-full.svg", "type": "image/svg+xml" },
    { "path": "skull-empty.svg", "type": "image/svg+xml" },
    { "path": "skull-break.json", "type": "lottie" },
    { "path": "crack.ogg", "type": "audio/ogg" }
  ],
  "provides": {
    "counter-icons": [
      { "key": "skull", "full": "skull-full.svg", "empty": "skull-empty.svg", "spend": "skull-break.json" }
    ],
    "table-widgets": [
      { "key": "fear", "view": "pips", "icons": "skull", "field": { "setting": "field" } }
    ]
  },
  "settings": [
    { "key": "field", "type": "system-field", "lives": "desk", "label": { "ru": "Поле Страха", "en": "Fear field" }, "level": "room" },
    { "key": "place", "type": "choice", "options": ["top", "side", "gm"], "default": "top", "level": "room" },
    { "key": "seen", "type": "choice", "options": ["all", "gm"], "default": "all", "level": "room" },
    { "key": "sound", "type": "toggle", "default": true, "level": "room", "personal": true }
  ]
}
```

Ключи внутри модуля — короткие (`skull`, `fear`); снаружи на них ссылаются полным именем `ashwood/skull-fear:skull`. Подписи всегда с переводами — сразу под рынки ЕС/США.

## Точки подключения первой версии

Каждая точка — запись в реестре ядра: имя, zod-схема элемента, где используется, запасной вариант. Новая точка — модуль плюс строка в реестре, как типы шагов.

| Точка | Что даёт модуль | Где используется | Уровни | Запасной вариант |
| --- | --- | --- | --- | --- |
| `fx` | анимация: файл Lottie, тип (`on-target`, `projectile`, `area`, `on-actor`), длительность, звук | шаг эффекта «показать эффект» | система, комната | встроенный пресет того же типа |
| `dice-skins` | вид кубов: картинки граней или Lottie броска | кубомёт, бросок дня | личный | стандартные кубы |
| `token-style` | рамка фишки, стиль полос, значки состояний | слой оверлеев фишек | система, комната, личный (только своя фишка) | стандартный стиль |
| `counter-icons` | иконки «заполнено / пусто / потрачено» + анимация смены | виды «Точки» и «Круг зарядов» | система, комната | кружки |
| `value-animation` | Lottie с размеченными кадрами под значения 0…N | вид «Анимация по значению» | система, комната | вид «Точки» |
| `table-widgets` | виджет HUD: поле стола или группы, вид, иконки, место, кто видит | HUD стола | система, комната | виджет не показывается |
| `content` | записи компендиума, эффекты, таблицы, раскладки листа для указанной системы | конструктор и компендиум | система | — |

**Правила для всех точек**

- Элемент проверяется схемой точки при публикации и при загрузке; не прошёл — используется запасной вариант, ошибка пишется в «Проблемы» комнаты для мастера.
- Визуальные точки (`fx`, `dice-skins`, `token-style`, `counter-icons`, `value-animation`, `table-widgets`) не меняют состояние игры — только показ.
- `content` меняет данные системы, поэтому сливается в систему только автором системы, через ту же проверку «Проблемами», что и ручная правка.

## Настройки модулей

Автор описывает настройки в манифесте данными; VTT сам строит экран настроек и проверку значений. Автор интерфейс не пишет.

**Типы настроек**

| Тип | Значение | Вид на экране |
| --- | --- | --- |
| `number` | число с `min`, `max`, `step` | «Минус и плюс» или «Ползунок» |
| `toggle` | да / нет | «Переключатель» |
| `choice` | один из `options` (с переводами подписей) | «Кнопки выбора» |
| `color` | цвет | палитра токенов темы плюс свой |
| `text` | короткая строка | поле ввода |
| `system-field` | тег поля системы; фильтры `lives` (`sheet`, `desk`, `group`) и тип значения | выбор из словаря полей системы |
| `asset` | ассет этого модуля нужного типа | галерея ассетов |

**Уровни и приоритет**

- У настройки `level`: `system` или `room` — кто её задаёт. `personal: true` разрешает игроку переопределить у себя.
- Значение берётся так: личное (если разрешено) → комната → система → `default`.
- Права: настройки комнаты меняет только ведущий; настройки системы — автор системы.

**Экран и синхронизация**

- В настройках комнаты у каждого включённого модуля свой раздел; поля рисуются галереей видов конструктора листа, отдельный редактор не нужен.
- Схема проверки строится из описания настроек: неверное значение не сохраняется, сервер проверяет то же самое.
- Изменение настройки комнаты рассылается всем по вебсокету (новое сообщение, по образцу `room:places`), клиенты применяют без перезахода.

**Обновление модуля**

Новые ключи получают `default`, удалённые игнорируются и не удаляются из базы (на случай отката версии), сохранённые значения не сбрасываются. Сменился тип ключа — значение сбрасывается на `default`, мастер видит предупреждение.

## Что добавить в ядро

Это фундамент: без него модули будут ломаться на каждом обновлении. Каждый пункт — сначала документ в `docs/`.

- **Публичное API движка.** Сейчас `packages/engine/src/index.ts` ничего не экспортирует, веб импортирует внутренности по глубоким путям. Нужен явный фасад с версией: расчёт листа, ход, словарь полей системы, реестры точек подключения. Всё остальное — внутреннее.
- **Версия ядра и схемы.** Номер версии ядра, который сверяется с `core` в манифесте; номер версии системы, который сверяется с `system`.
- **Пространства имён.** Всё, что приносит модуль (ключи ассетов, записи компендиума, эффекты, теги полей из `content`), получает префикс `автор/имя:`. Линт проверяет, что модуль не пишет в чужое пространство. Двоеточие в тегах уже запрещено схемой для своих целей — нужно согласовать разметку.
- **Шаг «показать эффект».** Новый тип шага в реестре движка: параметры — анимация (`fx` из модуля или встроенный пресет), откуда (действующий), куда (цели или область), когда (до броска, после попадания, после промаха, на крите). Шаг не меняет состояние: он добавляет в итог хода событие показа, сервер рассылает его вместе с дельтами, клиенты проигрывают. Повтор хода по журналу даёт то же событие.
- **Вид «Точки с иконками».** Расширение видов «Точки» и «Круг зарядов» (`docs/view-settings.md`): настройки `icons` (ссылка на `counter-icons`) и анимация при изменении. Без иконок — как сейчас.
- **Вид «Анимация по значению».** Новый вид числового поля: Lottie с разметкой кадров на каждое значение от `min` до `max`; при изменении значения проигрывается переход от текущего кадра к нужному. Обязателен верх, как у «Точек».
- **Виджеты HUD стола.** Поля, живущие у стола или группы (`field.lives: desk | group`, как Страх ведущего в Daggerheart), показываются виджетом с видом поля, местом на экране и правилом видимости.
- **Хуки слоёв canvas.** Слои оверлеев и эффектов принимают элементы из реестров точек `token-style`, `fx`; на вход только состояние на чтение.

Оба новых вида и виджеты HUD доступны и автору системы прямо в конструкторе, без модуля: хиты сердечками или заряды кристаллами ставятся на лист напрямую.

## Хранение и загрузка

**Сервер**

- Таблицы: модули (id, автор, статус), версии (манифест, хэши ассетов, статус модерации), включения (уровень, объект — система / комната / пользователь, модуль, версия, значения настроек).
- Ассеты лежат в объектном хранилище и раздаются через CDN с отдельного домена; путь содержит хэш файла, поэтому кэш вечный.
- Вход в комнату: в полном срезе приходит список включений (модуль, версия, итоговые настройки) и ссылки на манифесты.
- Изменение включения или настройки — дельта по вебсокету всем в комнате.

**Клиент**

- Загрузчик получает манифесты, проверяет их схемой, регистрирует элементы в реестрах точек.
- Ассеты грузятся лениво: при первом использовании (анимация — при первом показе, иконки — при первом виджете), с предзагрузкой того, что видно сразу.
- Кэш на устройстве по хэшу; на телефоне — с лимитом и вытеснением давно не использованного.
- Не загрузилось или не прошло проверку — запасной вариант точки, игра продолжается.

**Лимиты (стартовые, уточнить по замерам)**

- Один ассет — до 2 МБ, модуль целиком — до 20 МБ, Lottie — до 500 КБ.
- В комнате — до 20 включённых модулей.
- Только форматы из белого списка (см. «Безопасность»).

## Безопасность и правила сторов

**Файлы**

- Белый список: Lottie (JSON), PNG, WebP, SVG, OGG, MP3. Тип проверяется по содержимому, а не по расширению.
- SVG очищается от скриптов, обработчиков событий, внешних ссылок и `foreignObject`.
- В Lottie отключаются выражения (expressions): они могут содержать JavaScript. Анимация с выражениями отклоняется при публикации.
- Ассеты раздаются с отдельного домена, без cookie основного сайта.
- Лимиты размеров — из раздела «Хранение и загрузка».

**Данные**

- Манифест и данные проверяются zod-схемой и линтом при публикации, при загрузке и на сервере при включении.
- Модуль не может писать вне своего пространства имён и вне своих точек подключения.
- Визуальные точки не меняют состояние игры: сервер не принимает от них ничего.

**Модерация**

- Тексты и картинки проходят ИИ-модерацию, подозрительное — к человеку, как с постами в ScRoll.
- Жалоба на модуль из комнаты; модератор может снять версию — у комнат она отключается и заменяется запасным вариантом.

**Сторы**

- Модули-данные не являются исполняемым кодом, поэтому допустимы в приложениях iOS и Android. Модули с кодом в iOS-приложение, скорее всего, не пройдут — это одна из причин, почему первая версия без кода.
- Продажа модулей внутри мобильного приложения — цифровой контент, по правилам Apple требует встроенных покупок (IAP). Для платных модулей на старте: покупка через веб; перед запуском проверить актуальные правила Apple и Google с юристом.

## Мастерская и каталог

Мастерская — веб-приложение для компьютера, рядом с конструктором системы. Под телефон её не делаем: авторы работают за компьютером, на телефоне модули только включают и настраивают.

**Мастерская**

- «Мои модули»: создать, загрузить архив или файлы по одному, заполнить манифест формой (JSON руками не обязателен).
- Проверка как «Проблемы»: ошибки схемы, лимитов, безопасности — словами, с путём до места.
- **Песочница:** тестовая комната с образцовыми фишками и полями стола; кнопка «проиграть» для каждой анимации, переключатели настроек модуля, предпросмотр на ширине телефона.
- Шаблон модуля (по одному примеру на каждую точку подключения) и документация с примерами.
- Версии: черновик → на проверке → опубликован; опубликованную версию не правят, выпускают новую.

**Каталог**

- Поиск и фильтры: точка подключения, система, бесплатный / платный.
- Страница модуля: описание, превью (видео или гиф анимаций), версии с журналом изменений, отзывы и рейтинг (та же механика, что у приключений).
- Кнопка «включить в комнате» — для ведущего прямо со страницы модуля, с выбором комнаты.

**Платные модули**

- Покупает ведущий (или автор системы), работает у всего стола — игрокам платить не нужно. Личные модули покупает сам игрок.
- Выплаты авторам — через уже готовый Stripe Connect, комиссия платформы с продажи.
- В мобильном приложении — ограничения сторов (см. «Безопасность и правила сторов»).

## Этапы и задачи

Оценки — грубые, в человеко-неделях, с активным использованием ИИ; без дизайна ассетов и тестов с живыми мастерами.

**Этап 0. Фундамент (\~3–5 нед.)** — после стола на Skia (задачи по UX, раздел «Стол: как делаем»).

- [ ] **Публичное API движка и версии.** Фасад в `packages/engine/src/index.ts`, номер версии ядра и системы. Готово, когда: веб и мобилка импортируют движок только через фасад; тест проверяет, что глубоких импортов нет.
- [ ] **Реестр точек подключения.** Механизм регистрации точек с zod-схемой элемента и запасным вариантом. Готово, когда: точка добавляется модулем плюс строкой в реестре; незарегистрированный тип в манифесте отклоняется.
- [ ] **Пространства имён.** Префикс `автор/имя:` для всего, что приносит модуль; правило в линте. Готово, когда: два модуля с одинаковыми ключами не конфликтуют; запись в чужое пространство — ошибка «Проблем».

**Этап 1. Визуал без модулей (\~4–6 нед.)** — сначала встроенное, чтобы проверить точки на своих данных.

- [ ] **Шаг «показать эффект»** и 5–8 встроенных анимаций (попадание, промах, крит, лечение, снаряд, область). Готово, когда: атака в образце D&D проигрывает анимацию у всех за столом; повтор хода по журналу даёт то же событие.
- [ ] **Виджеты HUD** для полей стола и группы. Готово, когда: Страх в образце Daggerheart виден на HUD, видимость «только ведущий» работает, правка сразу у всех.
- [ ] **«Точки с иконками» и «Анимация по значению».** Готово, когда: автор ставит хиты сердечками в конструкторе без модуля; анимация по значению проходит 0→N и обратно без рывков.

**Этап 2. Модули (\~8–10 нед.)**

- [ ] **Схема манифеста и настроек** в `packages/schema`. Готово, когда: пример из раздела «Манифест» проходит проверку, испорченные варианты — нет, с понятной ошибкой.
- [ ] **Сервер: хранение, включения, CDN.** Готово, когда: ведущий включает модуль в комнате, игроки получают его без перезахода; версия закреплена.
- [ ] **Клиент: загрузчик, кэш, запасной вариант.** Готово, когда: модуль с битым ассетом не ломает стол; повторный вход в комнату не качает ассеты заново.
- [ ] **Настройки модулей:** автоэкран, уровни, приоритет, синхронизация. Готово, когда: модуль черепов из примера настраивается в комнате, звук отключается у одного игрока, у остальных остаётся.
- [ ] **Безопасность ассетов:** белый список, очистка SVG, запрет выражений Lottie, отдельный домен, лимиты. Готово, когда: SVG со скриптом и Lottie с выражением отклоняются при публикации; тесты на каждый случай.
- [ ] **Мастерская с песочницей** и шаблон модуля. Готово, когда: модуль черепов собирается в мастерской формой, без ручного JSON, и проверяется в песочнице.

**Этап 3. Каталог (\~4–6 нед.)**

- [ ] **Каталог:** поиск, страница модуля, версии, отзывы, модерация.
- [ ] **Платные модули:** покупка через веб, выплаты авторам через Stripe Connect. Готово, когда: ведущий купил модуль на сайте, и он работает в комнате на телефонах игроков.

Сначала 5–10 приглашённых авторов на этапе 2, открытый каталог — на этапе 3.

- Разметка пространств имён: двоеточие в тегах сейчас занято выведенными мишенями — какой разделитель для модулей?
- Комиссия платформы с продажи модулей и минимальная цена.
- Кто отвечает за лицензию контента в `content`-пакетах по чужим системам (SRD, хоумбрю, тексты из книг) и как это проверять при модерации.
- Может ли контентный пакет подключаться к чужой опубликованной системе без согласия её автора.
- Какие встроенные анимации и иконки рисуем сами к этапу 1, и кто их рисует.
- Платные модули в мобильном приложении: только покупка через веб или IAP для части рынков — решить с юристом до этапа 3.
