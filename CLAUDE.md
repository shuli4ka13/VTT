# CLAUDE.md

## Что это

Конструктор ролевых систем и чарников (VTT). Монорепо на TypeScript: движок
правил изоморфным пакетом, NestJS-сервер, React-веб. Пользователь-некодер
собирает систему, мир и чарники в интерфейсе — значит все три сущности
обязаны быть данными, а не кодом.

Работа идёт только в этом репо, ветка `cdm`; историю не переписывать (никаких rebase/force push).
Рабочая копия (worktree) создаётся от старой точки: до первой правки сверить её с `cdm`
(`git log --oneline HEAD..cdm | wc -l`) и подтянуть перемоткой (`git merge --ff-only cdm`) — экран владельца новее.
Образ `deploy/Dockerfile` — статика + API + вебсокет одним контейнером, sqlite в томе.
Локально и в облаке — всё нодой (`make ts`, веб :8300, сервер :8200).

## Правила работы

- Отвечать по-русски, структурно (заголовки, списки), с точными путями файлов;
  термин при первом упоминании — с кратким определением.
- Не поддакивать: вместо «ты прав» — конкретный ответ или конкретное несогласие.
- Владелец смотрит на экран, а не в код: в итоге — что изменилось и где это увидеть
  в интерфейсе, без жаргона и английских имён.
- Никаких комментариев в коде (inline, блочные, JSDoc).
- В коммитах не указывать соавторство (`Co-Authored-By` не писать). PR не открывать —
  работа идёт в своей ветке, владелец сам решает, как её забрать.
- До продакшна: никаких переводов старого формата данных в движке и сервере —
  формат меняется, образцы в `samples/` правятся под новый.
- Кривое место сносить и пересобирать по правилу, а не чинить заплатками поверх.
- Не собирается данными — дописать движок; данные под дыру движка не подгонять.
- UI: одно понятие — один редактор, одинаковый везде; сложность скрыта
  (пресет → шаги словами → «ещё»), без английских имён и подписей-простыней.
- Вопросы о правилах системы (D&D, Shadowrun и т.п.) решать по книге, не угадывать.
  Книг и выписок в репо нет (чужой текст): выписки Shadowrun (`docs/sr6-compendium.md`,
  `docs/shadowrun6.md`) лежат только на машине владельца и в git не входят, в облаке их нет.
  Если правило не выводится из выписок, образца или `docs/` —
  не выдумывать, вынести вопрос в итог.
- Перед большим изменением модели — документ в `docs/`, затем его проверяет советник (advisor);
  сверять с принятыми решениями (`docs/decisions.md` и документы моделей), а не с текущим кодом.
  Владельцу на одобрение модель не нести. Сабагент `reviewer` — только итоговый дифф ядра движка
  перед коммитом, один раз на задачу.
- Конструктор говорит словами автора правил: «носитель», не «я/меня».
- Реализацию по ясной спецификации отдавать сабагенту (`executor` — UI, тесты по образцу, приёмка,
  перевод данных; `haiku-coder` — механика, проверяемая тестом); себе — ядро движка, замысел,
  проверка диффа, один полный прогон затронутого пакета в конце.
- Облик экрана — по «библии» (коммит «style(vtt): облик под «библию»…»): индиго,
  `CardHead` серифом с квадратиком, капс только у шапок колонок, один цвет — одно
  значение («пока» зелёный, «когда» розовый, «Если» бирюзовый), таблицы строками
  с тонкими линиями, слова вместо ключей. В итоге перечислить, что проверить глазами
  (в облаке браузера нет).
- Правки узкие, без переформатирования и переписывания образцов целиком скриптом без нужды;
  коммиты мелкие по смыслу, `git add` явными путями, сообщения в стиле истории
  (`feat(vtt): …` по-русски).
- Переделал экран, шаг, формат или слово — переделай и урок этой темы в том же заходе (`apps/web/src/guide/lessons/`):
  тексты ходов, якоря, условие «пройдено», стартовый набор. Урок, который учит прежнему экрану, — поломка, а не долг.
  Проверка — `npx vitest run src/guide` в `apps/web`; в итоге назвать, какие уроки затронуты и что в них изменилось.
- Движок снаружи пакета берут только через фасад: `import … from '@vtt/engine'` (образцы — `@vtt/engine/samples`).
  Нужно новое имя — строка в рубрике `packages/engine/src/api/`, не глубокий импорт; тест `api.facade` это стережёт.
- Тесты — только ценные; узкий тест в цикле, тяжёлые наборы один раз в конце. Что гонять —
  скилл `checks` (`.claude/skills/checks/`), перед «готово» — обязательно.

Исходно проект существовал как ванильный JS-прототип (PoC: ноль зависимостей,
без сборки, 505 тестов). Движок портирован с него один в один — паритет был
закрыт отдельным тестом, — после чего старый слой удалён из рабочего дерева.
История и сам PoC остались в git (до коммита с удалением).

## Команды

```bash
make            # шпаргалка
make install    # зависимости (yarn workspaces) и git-хуки `.githooks/` (без соавторства, без комментариев)
make ts         # сервер :8200 и веб :8300 локальной нодой — только вне докер-стека
make ts-build   # собрать пакеты, сервер и веб в dist/
make ts-seed    # миры-образцы на сервер: шесть систем, каждая «· полный» и «· лёгкий»
make ts-test    # тесты всех пакетов
make ts-check   # проверка типов
```

В облаке: Node 24 (`.nvmrc`), `make install` в корне (иначе git-хуки не включатся); если тесты сервера или веба не видят пакетов — сначала `make ts-build`.

Стенд из рабочей копии — свои порты и своя база, чужие процессы и стенд владельца (:8301 / :8201) не трогать:
сервер `cd apps/server && VTT_PORT=8202 VTT_DB=<временный файл> npx tsx src/main.ts`, образцы
`VTT_URL=http://localhost:8202 npx tsx src/seed-run.ts`, веб `cd apps/web && VTT_WEB_PORT=8302 VTT_API_PORT=8202 npx vite --strictPort`.
Сервер запущен без слежения: после правки движка или образцов — `yarn build:packages`, перезапуск и чистая база;
веб после пересборки пакетов тоже перезапустить. Клиент и сервер разных версий не сходятся («сервер ответил не той формой»).

## Карта кода

| Где | Что |
|---|---|
| `packages/schema` | zod-схемы мира и API. Единый источник правды: клиент, сервер и валидация читают одни схемы |
| `packages/engine/src/index.ts`, `src/api/` | фасад движка — единственный вход снаружи пакета (`@vtt/engine`): шесть рубрик (расчёт, ход, проверка, словарь, реестры, форматирование) и `ENGINE_VERSION`; образцы — отдельный вход `@vtt/engine/samples` (`docs/engine-api.md`) |
| `packages/engine/src/formula/` | язык формул: `lex` → `parse` → AST → `evaluate`/`deps`. Вход только через `index.ts` |
| `packages/engine/src/engine/calc.ts` | `calc(system, sheet, tag, pass)`; проход несёт мемоизацию и ловлю циклов |
| `packages/engine/src/engine/modifiers.ts` | источники модификаторов, стакинг, помеха гасит преимущество |
| `packages/engine/src/engine/steps/` | тип шага = модуль за реестром (`prepare` — известное действующему, один раз; `finish` — на месте), ядро не правится и имён типов не знает |
| `packages/engine/src/core/` | ядро исполнения (план — `docs/core-v2.md`): одна операция мира `perform.ts` (действие, бросок по полю, вписать, надеть/снять, тип, группа, ход, новый лист), прогон `run.ts` (вызов, группа доставок с окнами вопросов, одна функция реакции `react`, «увидев кости», моменты, пересчёт, память «один раз на действие»), набор костей `dice.ts` и бросок `roll.ts`, сбор правок `edits.ts`, взгляд на лист `view.ts`, ключи `path.ts`, журнал внешнего `external.ts`, транзакции `state.ts`, права `authorize.ts` — один код для сервера, веба, пробы и тестов |
| `packages/engine/src/events/` | действия листа (`actions.ts`), шина подписок, моменты хода, жизненный цикл, сроки, связи, журнал строками |
| `packages/engine/src/model/` | типы, сериализация (сторож DTO), имена в формулах и проверка системы (`references.ts`, `lint.ts`), выбор входов кнопки (`buttons.ts`), переключатели крита и брони (`toggles.ts`) |
| `apps/server/src/` | NestJS: auth (вход по имени), catalog, worlds, rooms, `gateway/table.gateway.ts` (ws-канал стола), `db/` (drizzle поверх `node:sqlite`) |
| `apps/web/src/` | React: конструктор (`screens/constructor/`), компендиум, стол (`screens/play/`), zustand-сторы |
| `samples/` | миры-образцы — данные движка, `deploy/Dockerfile` копирует их в образ. У каждой системы полный мир (`*.world.json`, на нём все проверки) и лёгкий (`*.lite.world.json` — те же таблицы и листы, атака и лечение, малая книга; обязан быть частью полного — `tests/samples.lite.test.ts`) |

## Архитектура: главное

Подробности подгружаются сами, когда открыт файл из их области (`.claude/rules/`):
модель эффектов, таблиц и времени — `engine-model.md` (движок, схема, веб, образцы, `docs/`),
сервер — `server.md`, приёмка — `acceptance.md`.

**Три сущности, все — данные.** Система (поля, формулы, библиотека эффектов,
рода записей), чарник (чистый DTO: значения и ссылки, ничего вычисленного),
компендиум (предметы и действия — циферки и ссылки на эффекты). Считает движок,
один на программу.

**Инварианты, которые легко сломать:**

- **Стабильный тег.** У поля машинный `#tag` и человеческий `label`; формулы
  ссылаются только на тег. Переименование label не ломает ничего.
- **Ключ — латиница, человек его не видит.** Ключ (таблица, колонка, строка, эффект, вход, шаг, метка, блок, страница)
  делает конструктор из названия; название лежит подписью (`label`, у имени строки цикла `asLabel`, у имён договора
  метки `said`). Экран, журнал и «Проблемы» называют вещь подписью; ключом — только то, чего уже нет. Стерегут
  `samples.latin-keys` и `samples.problem-words` (движок), `no-keys` (веб). Модель — `docs/latin-keys.md`.
- **Хранимое ≠ вычисляемое.** Вычисленное никогда не попадает в DTO чарника;
  round-trip JSON обязан быть идентичным.
- **Движок не знает имён статов.** `str`/`hp`/`ac` в `packages/engine` или
  общем UI — ошибка: новый стат добавляется правкой данных.
- **Словарь мишеней выводится** из объявленных тегов системы, нигде не хранится.
- **Никакого `eval` / `new Function`.** Формула — строка данных, парсер свой.
- **Имя броска — бросок целиком.** У шага «Бросок» с костью или полем «сколько вышло всего» — итог через точку
  (`@бросок.total`), как «на костях»; голое имя — весь бросок, и стоит оно только целиком на стороне сравнения
  или во входе-броске вызова. Голое имя там, где ждут число, считается как «всего», но «Проблемы» это замечают
  (`docs/roll-total.md`). Шаг-расчёт без кости — само число.
- **Операция — одна чистая функция** (`core/perform.ts`; действие — `core/act.ts: runAct`): снимок листов + операция + журнал → итог или вопрос. Режимы: настоящий, проба, предпросмотр.
  Пределы (`core/limits.ts`, данные системы с умолчаниями): обработчик в стеке не больше 4 раз, бюджет 32 вложенных вызова на одну цепочку реакций, 16 уровней вложенности вызовов, 8 кругов пересчёта, 8 пересчётов в одном окне вопросов (`probes`); предел — отказ обработчика с откатом и строка `CUT_WORDS` / `PROBES_WORDS` в журнале.
  Вопрос игроку останавливает выполнение; сервер хранит намерение, снимок, журнал (кости и ответы по ключам-путям) и вопрос, а на ответ выполняет действие заново — оно детерминировано и доходит до того же места. Пока висит вопрос, листы комнаты не правятся; ведущий может отменить действие (`room:cancel`).

**Слова — данные, а не литералы.** Подписи шагов и общие слова живут в
`packages/engine/src/words/`; `apps/web/src/words.ts` реэкспортирует их.
Тест `apps/web/src/words.test.ts` запрещает старые синонимы и латинскую
запись костей во всех четырёх пакетах.

**Проблемы системы считает движок.** `model/references.ts` + `model/lint.ts`
дают находки словами экрана с адресом (вкладка, эффект, шаг). Сервер не
публикует систему, в которой линт нашёл ошибку.

**Журнал и детерминированность.** Движок не знает ни случайности, ни времени, ни id — их подаёт сервер (`DIE`, `CLOCK`, `IDS`); тест `engine.pure` это стережёт. Каждый принятый ход комнаты пишется в `room_journal`: кто, намерение, выпавшие кости, итог (`RoomsService.recorded`, кость ловит `AsyncLocalStorage`); сыгранное заново по журналу обязано совпасть (`test/journal.test.ts`).

**Омоним «токен»:** фишка на карте (VTT-слой) и единица разбора (парсер) —
разные вещи, различать в именах.

**Одно понятие — один редактор.** Название, вызов эффекта с аргументами, выбор значения (число /
формула / поле / свойство), шаг, выдача, модификаторы, блок — у каждого один компонент, одинаковый везде,
где понятие встречается. Редкие настройки — под «ещё», а не отдельными полями и подписями.

**Граница режимов держится импортами:** экран игрока не импортирует редакторы
полей; правит теги — только автор. Закрыто тестами.

## Процесс

- Сознательные упрощения фиксировать в `docs/production-differences.md`.
- Тесты — четыре места: `packages/schema`, `packages/engine`, `apps/server`, `apps/web`; когда какие — скилл `checks`.
  Снимков «как было» (золотых снимков) нет: тест проверяет правило, а не запоминает прежний вывод.
  «Образцы играются» (`packages/engine/tests/samples.play.test.ts`): в каждом образце каждое действие каждого листа
  и бросок по полю каждого вида отрабатывают или отказывают по правилам; `PLAY_SEEDS=3` — полный перебор (~3 мин).
- Тяжёлые прогоны — по одному за раз: остановленный фоновый прогон оставляет рабочие процессы, они делят ядра
  со следующим и дают ложные падения по времени. Перед новым — проверить, что прежних процессов нет; после каждой
  правки не перезапускать, один полный прогон в конце.
- Умолчания в данных не пишутся: редактор, получив значение по умолчанию, снимает ключ.
- Контракт парсера формул — `docs/parser-plan.md`: замена реализации обязана
  пройти те же тесты.
