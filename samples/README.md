# samples/ — образцовые миры как данные

Два файла — `dnd5e.world.json` и `cyberpunk.world.json` — то, что раньше
жило кодом в `packages/engine/src/model/{system.ts, system-cyberpunk.ts,
compendium.ts, sheets.ts}`. Решение: образцовые системы обязаны быть ДАННЫМИ,
которые мог бы выгрузить сам конструктор, а не TS-модулями. Модули с той же
информацией противоречили бы собственному тезису проекта — «система лежит
данными, а не кодом» — просто на уровень выше, в исходниках самого движка.

Формат файла — ровно то, что раньше собирала `sampleWorlds()` в
`apps/server/src/seed.ts`:

```json
{ "title": "…", "system": { … }, "compendium": { "items": […], "actions": […] }, "sheets": [ … ] }
```

Единственная точка доступа из кода — `packages/engine/src/model/systems.ts`:
она импортирует эти два файла и экспортирует `SAMPLE_SYSTEMS` (массив
`system`-частей, как раньше) и `SAMPLE_WORLDS` (мир целиком: `title` +
`system` + `compendium` + `sheets`). Больше никто эти JSON-файлы напрямую
не читает.

Переносом занимался одноразовый node-скрипт (жил в scratchpad, в репозиторий
не попал): он импортировал старые ts-модули как есть и записывал их
in-memory объекты в JSON. Ни один байт данных не переписывался руками —
только упаковка. Побайтная сверка (`JSON.parse(файл)` структурно и строково
идентичен исходному объекту) прогнана и прошла для обоих миров.

## Что здесь было раньше — знания, а не данные

Ниже — комментарии из удалённых ts-модулей, ради которых имеет смысл
заглянуть в историю задачи. Сами данные, которые они поясняли, теперь
лежат в JSON рядом; пояснения остаются здесь, потому что они про решения,
а не про конкретные цифры.

### Было в `packages/engine/src/model/system.ts` (мир «D&D 5e»)

> Система — это ДАННЫЕ. Ни одной функции в этом файле нет и быть не должно.
> Срез D&D 5e: шесть характеристик → модификаторы → бонус мастерства таблицей →
> один навык → класс брони с условием → атака, спасбросок, лечение и ответка.
>
> Система = поля + БИБЛИОТЕКА ЭФФЕКТОВ + список включённых на всех.
> Эффект — единица автоматизации; всё, что мир делает сам, лежит в `effects`.
>
> Три способа получить значение поля (`value.kind`):
>   stored  — лежит в чарнике; здесь только тип и значение по умолчанию
>   formula — строка на языке формул, ссылается на другие поля через #тег
>   table   — поиск по диапазонам в system.tables, аргумент — формула
>
> Список мишеней для эффектов и бонусов нигде отдельно не хранится: он выводится
> из объявленных здесь тегов (см. src/engine/targets.js).

> «Срез» из ТЗ — узнаваемый КОНЕЧНЫЙ поднабор правил, не вся 5e. Это
> оговорка для разработчика, имени системы она не принадлежит: имя видят
> игроки в списке миров.

> Именно таблица по диапазонам, а не формула: в 5e это ступенька,
> и выводить её из уровня арифметикой — подгонка под конкретную систему.
> (о `tables.proficiency`)

> Какие механики преимущества включены в комнате. Список самих механик
> с примерами из разных систем — в src/model/advantage-methods.js.
> (о `advantage.methods`)

> Константы системы — доступны правилам наравне с полями листа.
> Первая — ведущая кость: что бросается для действий в этом мире.
> Определение описывает и состав броска, и что возвращается; total есть
> всегда (см. src/engine/lead-die.js). Смена sides здесь меняет ВСЕ броски,
> не требуя правки ни одной формулы.
> (о `constants.lead_die`)

> Экономика действий: словарь системы, как мишени бросков. Раундов в PoC
> нет, поэтому это РАЗМЕТКА (бейджи и группировка кнопок), не запрет.
> Лимиты повесятся на готовый словарь, когда появятся ходы.
> (о `action_types`)

> ── БИБЛИОТЕКА ЭФФЕКТОВ ───────────────────────────────────────────────────
> Одно определение на систему. Запись компендиума ссылается на эффект
> по имени и приносит только аргументы — копий шагов в записях нет
> и быть не может: правка эффекта обязана менять все записи сразу.
>
> Эффект не знает слова «урон»: удар, спасбросок, лечение — разные
> заполнения одних и тех же слотов. Типы шагов — src/engine/steps/.

> ЗАКОН МИРА пишется прямо в шагах, а не спрашивается у записи. «Бьём
> против класса брони» и «урон идёт в хиты» — это правила 5e, и меч
> о них ничего не знает: у меча спрашивают ровно то, что от меча к
> кинжалу разное, — кость урона.
>
> Отсюда три способа заполнить слот, и каждый на своём месте:
>   { expr } / { tag } / { const } — закон мира, один на всю систему
>   { prop }                       — то, что разное У КАЖДОЙ ЗАПИСИ
>   { param }                      — то, что разное У КАЖДОГО РОДА
>                                    (или что обязана посчитать цель)

> Единственный законный параметр во всей системе — и вот почему он
> законный: чем спасается цель, знает ТОЛЬКО цель, своим листом.
> Выражение обязано уехать в конверт неразрешённым (`of: 'target'`),
> а такое умеет лишь параметр: { prop } подставил бы строку как есть.
> (об эффекте `save`, параметре `save`)

> Порог на стороне цели: бросает ПОЛУЧАТЕЛЬ своей ведущей костью
> и своими модификаторами. Дальше — только если НЕ спасся.
> (о шаге `save` эффекта «Спасбросок»)

> Лечение — НЕ урон с минусом: направление «плюс», потолок — максимум
> хитов, сопротивления не участвуют. Другое заполнение тех же слотов.
> (об эффекте `heal`)

> Тот же шаг «состояние», другое направление: лечащее заклинание
> снимает яд. Отдельного типа шага для этого не нужно.

> ── пассивные: висят и правят цифры ────────────────────────────────────
>
> Помеха — не «−2 к броску». Это другая порода: два кубика, берём худший.
> (об эффекте `poisoned`)

> Мишень «входящее» — то, что летит В поле извне. Шаг «применить»
> прогоняет через неё величину, когда правило сказало «с учётом
> модификаторов цели»; лечение и износ идут мимо.
> (об эффекте `stoneskin`, мишени `incoming:hp_current`)

> Правила комнаты — те же пассивные эффекты, просто включённые на всех
> (см. grants системы ниже). На карточке эффекта про охват ни слова:
> эффект не знает, где он подключён.
> (об эффектах `heavy_armor_rule`, `mastery_rule`)

> ── триггерный: срабатывает сам на чужое событие ────────────────────────
>
> Когда по владельцу попали атакой — бьёт нападавшего в ответ.
> Слушаем эффект «Атака», момент — после разрешения на владельце,
> условие — по трассе события: попали ли. Условие структурное,
> как слоты шагов: { ref } смотрит в результат шага события.
>
> У триггера нет записи компендиума, которая заполнила бы дырки, —
> он сам себе источник. Значит и дырок быть не должно: всё вписано.
> (об эффекте `thorns`)

> Правила комнаты: пассивные эффекты, включённые на ВСЕХ чарников мира.
> Ссылки, а не копии — тот же эффект можно и повесить на одного.
> (о `grants` системы — то же «что висит», что у вещи, типа листа и эффекта)

> Словарь РОДОВ записей компендиума. Род — это ФОРМА ЗАПОЛНЕНИЯ: он
> объявляет, какие циферки спросить у человека (`props`) и к каким
> эффектам их привязать (`bindings`). Тогда наполнение сводится к вводу
> заранее известных чисел, а действия у записи появляются сами.
>
> `kind` — базис хранения, короткий словарь движка (item / action).
> Всё человеческое — лейбл, подсказка, значок, группа — дело системы.
> (о `records`)

> Протягивание: род привязан к эффекту, запись только заполняет циферки.
> Надел меч — получил «Атаку», снял — потерял. Аргументы ЕСТЬ: они
> закрывают потребность эффекта в кости урона свойством записи —
> ни против чего бьём, ни куда наносим меч по-прежнему не знает,
> это законы мира, и они вписаны в сам эффект.
> (о `records.weapon.bindings`)

> Мишени бросков — то, на что вешаются модификаторы породы «правящие бросок».
> (о `rolls`)

> Текстовые поля: значение вводит игрок, формулы на них не ссылаются.
> В черновике это был блок «Поля персонажа» — имя, раса, класс.

> Условное правило: в тяжёлом доспехе Ловкость не прибавляется.
> (о поле `ac`)

### Было в `packages/engine/src/model/system-cyberpunk.ts` (мир «Киберпанк»)

> Система B приёмочного теста: срез киберпанка. Доказательство модели:
> от 5e она отличается ТОЛЬКО данными — другая ведущая кость, другие поля,
> другой удар. Движок один, и этот файл не импортирует из него ничего.
>
> Модель боя:
>   порог:     1d10 + навык  против  сложности (число из записи)
>   величина:  2d8  ИЛИ  фиксированный урон предмета — выбирает запись
>   сравнение: величина против брони цели; меньше — цепочка обрывается
>   применить: минус из хитов на разницу (величина − броня)
>   применить: минус 1 из прочности брони — удар изнашивает снаряжение
>
> Здесь же второй способ подключить эффект: у ножа СВОЯ активность
> с готовыми аргументами (штучная вещь), а не привязка рода, как у меча в 5e.

> Рода записей ЭТОЙ системы: заклинаний в мире хрома нет — и в палитре
> компендиума их не будет. Рода выводятся из системы, а не из движка.
> (о `records`)

> Пассивный эффект второй системы: та же порода «правящий бросок»,
> другая система, тот же движок.
> (об эффекте `wired`)

> Правил комнаты в этом мире нет — секция необязательна.
> (о пустом `grants` системы)

> Своя активность: аргументы прописаны у самой записи, а не взяты
> из привязки рода. Так живут штучные вещи. damage_flat закрыт
> свойством самой записи — потребность эффекта, не прямое чтение.
> (о `mono-knife.activities`)

> Запись-действие: пистолета-предмета в срезе нет, а стрелять надо.
> Ссылается на тот же эффект с другими аргументами — величина своим броском.
> (о записи-действии `gun`)

### Было в `packages/engine/src/model/compendium.ts` (компендиум мира «D&D 5e»)

> Компендиум — данные для системы и чарника. Чистые данные плюс ссылки;
> ни одного шага автоматизации здесь нет и быть не может.
>
> Что запись умеет, объявляет её РОД в системе (`system.records[rk]`):
> какие циферки спросить у человека (`props`) и к каким эффектам их привязать
> (`bindings`). Поэтому наполнение сводится к вводу заранее известных чисел —
> у меча спрашивают только кость урона, а «Атака» появляется у владельца сама.
>
> Модификатор ссылается на `target` — тег, объявленный в системе. Ничего,
> кроме объявленных тегов, здесь встретиться не может: проверка
> в src/engine/targets.js падает на неизвестной мишени.
>
> Две породы модификаторов, и это принципиально:
>   kind: 'value' — правит ЗНАЧЕНИЕ, обычная арифметика, складывается по правилу стакинга
>   kind: 'roll'  — правит БРОСОК, не число, не складывается, помеха гасит преимущество

> Оружие. Действий у записи своих НЕТ: «Атаку» даёт привязка рода
> (system.records.weapon.bindings). Заполнена одна циферка — кость урона.
> Надел — получил атаку, снял — потерял, как в Foundry.
> (о записи `longsword-item`)

> Действия — записи компендиума, а не законы мира.
>
> «Ядовитые брызги» — конкретная запись, как кольчуга; законом остаётся
> ЭФФЕКТ «Спасбросок» в системе, на который эта запись ссылается через род.
> Отсюда и граница режимов: запись ссылается только на УЖЕ объявленные теги
> и эффекты, нового не вводит — значит, завести её волен игрок, а не только автор.
>
> Заклинание — не отдельный род хранения, а род записи с группой
> «Заклинания»: подвиды (атакующие, лечащие, нейтральные) — это рода
> в одной группе, как поля листа раскладываются по блокам.
> (об `actions`)

Компендиум киберпанка (`cpCompendium`) отдельного файла-комментария не имел —
его пояснял общий блок наверху `system-cyberpunk.ts` выше.

### Было в `packages/engine/src/model/sheets.ts` (чарники «Арвен» и «Мирра»)

> Чарники — чистые DTO. Только сохранённые значения.
> Ни одного вычисленного числа здесь нет и появиться не может: сериализатор
> отвергает всё, что не скаляр (см. src/model/serialize.js).
>
> Оба персонажа считаются по одной и той же системе — dnd5e-slice.

> Меч надет — его атака появляется в действиях сама, по активности предмета.
> (о `arven.equipped`)

Чарники киберпанка (`silver`, `raze`) жили в `system-cyberpunk.ts` без
отдельных комментариев — их описывал общий блок наверху того файла.

## Что НЕ переехало

Три хелпера из `compendium.ts` — `findItem`, `findAction`, `allRecords` —
были функциями, не данными: искали запись по `id` в захардкоженных `items`/
`actions` этого конкретного модуля. Единственный вызов (`findItem` в
`tests/rule.weapon.test.ts`) заменён на прямой `.find()` по компендиуму
образца — поведение теста не изменилось, отдельного модуля-обёртки эти три
строчки не стоят.
