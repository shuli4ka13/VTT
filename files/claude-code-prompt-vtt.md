# Промпт для Claude Code: прототип конструктора чарников (VTT)

> Вставить первым сообщением в новой сессии Claude Code в пустом репозитории.
> Можно также сохранить в корень репо как `CLAUDE.md` — тогда контекст подхватится автоматически при каждом запуске.

---

## Задача

Собрать proof-of-concept конструктора ролевых систем и чарников. Цель — доказать, что концепт нормально программируется, а не сделать продукт. Красота интерфейса не важна, важна архитектура.

## Жёсткие ограничения стека

- Vanilla JavaScript, ES modules. **Без фреймворков** (никакого React/Vue/Svelte).
- **Без TypeScript.**
- **Без бэкенда.** Всё в браузере, данные в памяти.
- **Без рантайм-зависимостей.** npm-пакеты не подключать вообще.
- Запуск: `python3 -m http.server` из корня (нужен из-за CORS на `file://`).

## Три сущности

1. **Система** — законы: какие поля бывают, как считаются формулы, как листы реагируют на события. Это данные, а не код.
2. **Чарник** — заполненный лист. **Чистый DTO**: только сохранённые значения, никаких методов, никаких вычисленных величин.
3. **Компендиум** — библиотека записей: предметы, эффекты. Ссылается на теги, объявленные в системе.

Все три создаются пользователем-некодером в интерфейсе. Значит все три обязаны быть данными.

## Ключевые правила архитектуры

**Стабильный тег.** У каждого поля есть машинный `#tag` и человеческий `label`. Формулы ссылаются **только на тег**. Переименование `label` не должно ломать ничего. Отождествление тега и лейбла — запрещено. Тег генерируется при создании поля и дальше неизменен.

**Хранимое и вычисляемое строго разделены.** Вычисленные значения **никогда** не попадают в DTO чарника. Приёмочный тест: сериализовал чарник в JSON, распарсил обратно, сравнил — должно совпасть побайтно.

**Никакого `eval` и `new Function`.** Формула — строка данных, её разбирает собственный парсер. Исполнение пользовательского текста как кода запрещено категорически (дыра безопасности в мультиплеере + тихие поломки).

**Система задаёт словарь мишеней.** Список того, на что могут ссылаться эффекты и бонусы предметов, выводится из объявленных в системе тегов. Отдельно он нигде не хранится.

## Что строим — по фазам

Делать строго по порядку, каждую фазу доводить до рабочего состояния и останавливаться для ревью.

### Фаза 0 — скаффолд

Структура папок, `index.html`, точка входа как ES-модуль, `README.md` с командой запуска. Завести `docs/production-differences.md` — лог мест, где прототип сознательно наивен (туда пишем по ходу всех фаз).

### Фаза 1 — модель данных

Модули с примерными данными: система, два чарника, компендиум из одного предмета и одного эффекта. Только структуры, никакой логики.

Функция сериализации + тест round-trip для чарника.

### Фаза 2 — парсер формул

**Эту фазу не реализовывать.** Вместо кода:

- описать в `docs/parser-plan.md` предлагаемую архитектуру: лексер → AST → интерпретатор по дереву;
- зафиксировать грамматику: числа, `+ - * /`, скобки, унарный минус, функции `floor`, `ceil`, `min`, `max`, ссылки вида `#tag`, сравнения и тернарный оператор (нужны для условных правил вроде класса брони);
- определить интерфейс модуля: что на входе, что на выходе, какие ошибки;
- написать набор тестов (входная строка → ожидаемый результат), которые пока падают.

Реализацию парсера пишет человек. Дальнейшие фазы строить так, чтобы они зависели только от интерфейса модуля.

### Фаза 3 — движок вычислений

`calc(system, sheet, tag)`: находит поле по тегу, если формулы нет — берёт значение из чарника, если есть — вычисляет.

Требования: мемоизация в пределах одного прохода, обнаружение циклических зависимостей с внятной ошибкой, извлечение списка зависимостей из формулы. Движок не должен знать ни одного конкретного имени стата.

Пересчёт пока полный, инкрементальный по графу — позже. Записать это в лог отличий.

### Фаза 4 — модификаторы

Конвейер: **источник → условие → цель → правило стакинга**. Источник — предмет или эффект. Цель — тег. Условие — выражение.

Два разных вида модификаторов, и это принципиально:
- **правящие значение** (кольчуга: +2 к КД) — обычная арифметика;
- **правящие бросок** (преимущество: два d20, берём лучший) — не число, не складываются, помеха гасит преимущество.

Заложить оба вида сразу, даже если второй пока не используется.

### Фаза 5 — событийный конверт

Отправитель собирает конверт намерения (например: спасбросок по тегу, сложность, эффект при провале) и отправляет. **Отправитель ничего не считает за получателя.** Получатель распаковывает, считает по своей системе своими формулами и применяет к себе.

### Фаза 6 — минимальный интерфейс

Паттерн `render(state)` — полная перерисовка на любое изменение. Пометить в логе отличий как заведомо наивное.

Экраны: список статов чарника с вычисленными значениями; панель редактирования формулы.

**Критично в панели формул:** зависимости — кликабельные чипсы. Клик вставляет в формулу **тег**, а на экране формула отображается **лейблами**. Пользователь никогда не печатает тег руками и в норме его вообще не видит.

## Содержание примерной системы

Срез D&D 5e — узнаваемый и конечный:

- шесть характеристик (хранимые значения);
- модификатор = `floor((характеристика - 10) / 2)` — формула от другого поля;
- бонус мастерства от уровня — **таблица по диапазонам**, не формула. Нужен механизм описания таблиц;
- один навык = модификатор + бонус мастерства при владении;
- класс брони = база доспеха + Ловкость, **но в тяжёлом доспехе Ловкость не прибавляется** — формула с условием;
- одна атака: бонус атаки, урон кубами, событие по цели.

Заклинания и состояния не трогать — это компендиум, следующий заход.

## Черновик тимлида как источник UX

В `reference/index.html` лежит HTML-черновик от тимлида (один файл, интерфейс без движка). Прочитать и забрать оттуда **решения интерфейса и словарь понятий**:

- палитра блоков и декомпозиция на вкладки: чарники / предметы / эффекты / система;
- панель формул с кликабельными чипсами зависимостей;
- вкладка «Система»: выбор механик преимущества с примерами из разных систем (5e, WFRP, Fate), авто-правила вида «ярлык + условие + эффект + метод»;
- редактор предметов (свойства: урон, защита, бонусы, слоты, требования) и эффектов (тип, длительность, механика).

**Не смотреть вовсе** (к проверке концепта не относится): календарь, карта и сцены, токены, часы прогресса, чат и разбор бросков, радиальное меню, инициатива, сохранение и экспорт, ведущая кость, прогрессия.

**Не заимствовать:** способ хранения данных и вычисления. В черновике формулы подставляются по отображаемому имени поля и исполняются через `Function()` — оба решения запрещены выше по этому файлу. Условия авто-правил там сохраняются, но не вычисляются — движка за ними нет.

## Критерии приёмки

1. Round-trip JSON чарника даёт идентичный объект; вычисленных значений в нём нет.
2. Переименование `label` любого поля не ломает ни одной формулы.
3. Добавление нового стата и нового предмета с бонусом происходит **только правкой данных**, без единой строчки в движке.
4. Два чарника разных персонажей считаются по одной и той же системе.
5. Событие от одного чарника меняет значение у второго, причём расчёт происходит на стороне получателя.
6. Поиск по репозиторию не находит `eval` и `new Function`.
7. Циклическая формула даёт внятную ошибку, а не зависание.

## Требования к процессу

- Работать в отдельной ветке, финал оформить как PR. В `dev` не пушить.
- Модули маленькие, одна ответственность на файл.
- Комментарии там, где решение сознательно упрощено, с пометкой «в продакшне иначе» и записью в `docs/production-differences.md`.
- Тесты — отдельная страница `tests.html`, которая импортирует модули и печатает результат в консоль. Без тестовых фреймворков.
- В конце каждой фазы — короткая сводка: что сделано, какие решения приняты, что осталось спорным.
- Написать `ARCHITECTURE.md`: три сущности, поток данных, где живёт какое решение. Не больше страницы, простым языком.

## Чего делать нельзя

- Привязывать формулы к отображаемому имени.
- Хранить вычисленные значения в чарнике.
- Использовать `eval` / `new Function` / динамическое создание кода.
- Тащить зависимости, фреймворки, сборщики, TypeScript.
- Реализовывать парсер формул (фаза 2 — только план, интерфейс и падающие тесты).
- Уходить вперёд по фазам без остановки на ревью.
