# Дорожная карта переезда на TypeScript

Спека: [../specs/2026-08-07-ts-rewrite-design.md](../specs/2026-08-07-ts-rewrite-design.md)

Переезд слишком велик для одного плана, поэтому он разрезан на этапы.
Каждый этап — самостоятельный кусок работающего, тестируемого софта.
**Детальный план этапа пишется после закрытия предыдущего**: планы поздних
этапов зависят от API, которые затвердевают в ранних. Готов только план
этапа 1 — [2026-08-07-stage-1-engine-port.md](2026-08-07-stage-1-engine-port.md).

Сквозное правило всех этапов: PoC в корне заморожен (`src/`, `tests/`,
`server/`, `*.html` не правятся), паритет-тесты следят, чтобы новый движок
считал те же числа.

## Этап 1 — монорепо + перенос движка ✎ план готов

pnpm workspaces; `packages/engine` — перенос `src/formula`, `src/model`,
`src/engine`, `src/events` на TS один-в-один; тесты PoC — в Vitest;
паритетный контроль старый↔новый на образцовых мирах.

**Готово, когда:** все перенесённые тесты зелёные в Vitest; паритет-тест
зелёный; `node tests/run.js` в PoC по-прежнему даёт 505; в `packages/engine`
ноль рантайм-зависимостей (закрыто тестом).

## Этап 2 — packages/schema: типы и валидация мира

Zod-схемы `System` / `Sheet` / `Compendium` / `World` / `Envelope`; типы
через `z.infer`; черновые типы движка из этапа 1 заменяются выведенными.

**Готово, когда:** `мир.json` обеих образцовых систем (и v1-мир через
`migrate`) проходит parse и round-trip без потерь; движок типизирован
схемными типами; критерий №1 переписан тестом нового стека.

## Этап 3 — apps/server: NestJS

Модули `AuthModule` / `WorldsModule` / `RoomsModule` / `TableGateway`
(WebSocket, `@nestjs/platform-ws`); SQLite + Drizzle (мир — JSON-колонка,
валидируемая схемой); ход разрешается `exchange`-ом из `packages/engine`;
валидация входа — Zod-pipe, class-validator не заводится.

**Готово, когда:** e2e (supertest): вход по имени → публикация мира →
комната → ход с триггерной ответкой → дельты обоим подключённым; загрузка
v1-мира мигрирует; сервер отвергает намерение, не проходящее схему.

## Этап 4 — apps/web: каркас

Vite + React 19; роуты четырёх экранов (граница режимов — импортами и
роутами, как в PoC, закрыта тестом); Zustand + TanStack Query; загрузка и
сохранение мира через сервер; типизированный fetch-клиент поверх DTO
из `packages/schema`.

**Готово, когда:** мир открывается с сервера, значения листа считаются
`packages/engine` в браузере, правка хранимого значения видна сразу.

## Этапы 5–10 — фронт (после каркаса)

| # | Этап | Готово, когда |
|---|---|---|
| 5 | **Кирпичи**: дизайн-токены одним CSS-файлом; примитивы — карточка, строка-поле, сегментный переключатель, сворачиваемая секция, чипс, пустое состояние, бейдж вердикта; инлайн-стили запрещены линтером | Каталог примитивов рендерится на служебной странице; линтер валит `style=` |
| 6 | **Каркас экрана**: колонки делят ширину по надобности; секции боковых колонок сворачиваемые, с явными границами | Палитра не обрезается на 1440px; секции переставляются данными, не кодом |
| 7 | **Конструктор → Лист**: блоки, поля, панель формулы с чипсами (вставка в позицию курсора — из черновика), палитра доноров | Сценарий «пустая система → лист 5e из доноров» проходит мышкой |
| 8 | **Конструктор → Эффекты**: реестр видов слотов (компонент на вид); карточка шага — 8 решений, умолчания свёрнуты в строку-сводку; приговор привязан к карточке виноватого шага; род — компактный переключатель | «Атака 5e» собирается с нуля мышкой; приговор указывает на шаг |
| 9 | **Записи + Компендиум**: род = форма, запись = заполнение формы; протягивание видно | Сценарий «род оружия → меч → атака у владельца» проходит мышкой |
| 10 | **Лист игрока → Стол**: лист (правая колонка — в первую очередь); стол на PixiJS вне React; дельты по WS | Двое в комнате: ход одного меняет лист второго; печать в чате не дёргает карту |

**Вехи показа:** после этапа 8 конструктор можно показывать команде;
после этапа 10 — играть за столом.
