# Слот «источник величины» урона и структурный результат проверки

*30.07.2026. По итогам разбора урона на созвоне: доказать кодом, что «правило —
это данные со слотами», на самом маленьком возможном примере.*

## Задача

Из разбора двух моделей урона (D&D 5e и Shadowrun) следуют два требования к каркасу:

1. **Результат проверки — структура, а не флаг.** Минимальный состав: вышло или
   нет, превышение, что выпало на костях. Если движок отдаёт булево, модель
   «урон из степеней успеха» не выражается никакими настройками.
2. **У величины урона есть слот «откуда берётся»:** свой бросок (5e) или
   превышение из предыдущего шага (Shadowrun). Одна развилка в данных, не два движка.

Лакмус, которым проверяется каркас: одна и та же запись «Удар длинным мечом»,
один и тот же движок; две системы, отличающиеся **одной строкой данных**, дают
урон по модели 5e и по модели Shadowrun.

## Что сейчас (src/events/envelope.js)

- Получатель считает `hit = attack.total >= value` — булев флаг. Превышение
  вычисляется неявно и выбрасывается.
- `send` бросает кости урона сразу и кладёт в конверт готовый `total` — величина
  финализирована до того, как превышение стало известно.
- `damageOf` безусловно требует нотацию костей — фиксированный урон оружия
  (число без костей) невыразим.

Модель Shadowrun невыразима трижды. Это не баг реализации, а отсутствие слота.

## Решение

### 1. Результат проверки — структура (строит получатель)

```
check = {
  success: boolean,        // вышло или нет
  margin:  number,         // превышение: бросок − против-чего; отрицателен при промахе
  dice:    { rolls, kept } // что выпало на костях — нат-20/1 различимы по кубу, не по сумме
}
```

- Для атаки: `margin = attack.total − значение versus`. Строит получатель —
  только у него есть значение `versus`.
- Для спасброска: `margin = save.total − dc`. Спасбросок — тоже проверка,
  каркас один.
- В отчёте `check` **заменяет** прежние `hit` и `success` (одно место истины,
  а не флаг рядом со структурой).

### 2. Слот источника — в системе, не в действии

```js
// src/model/system.js
rules: {
  attack: {
    damage: { source: 'roll' },   // 'roll' — свой бросок (5e) | 'margin' — превышение (Shadowrun)
  },
},
```

- **Почему в системе:** запись компендиума не может переопределять форму
  разрешения — по границе режимов «меняет форму — только автор». И буквально
  «сколько систем, столько вариантов удара» при одной записи меча.
- Отсутствие секции ⇒ `'roll'`: все существующие данные работают без правок.
- `send` читает слот **своей** системы и штампует его в конверт
  (`onHit.damage.source`). Инвариант «отправитель ничего не считает за
  получателя» цел: слот — рецепт, а не значение получателя.
- Неизвестное значение слота — внятная `EngineError`, и в `send` (быстрый фейл
  у автора), и в `receive` (конверт мог прийти откуда угодно).
- Спасбросок слот **не** читает: что такое «превышение» спасброска, словарь
  намерений пока не определяет. Жёстко `'roll'`.

### 3. Конверт: урон отправителя — свои числа, без финала

```
onHit.damage = { notation, rolls, bonus, base, source }
```

`base` = сумма костей + бонус — всё, что отправитель знает сам. Финальный
`total` рождается **у получателя**:

```
total = base + (source === 'margin' ? check.margin : 0)
```

Отчёт получателя несёт разложение целиком — это зародыш живой трассировки:

```
report.damage = { notation, rolls, bonus, base, source, margin, total }
```

- `margin` в отчёте урона: число при `source: 'margin'`, иначе `null`.
- Урон применяется и показывается только при `check.success` — «урон только
  при попадании» в обеих моделях. Разбор конверта (сторожа) выполняется
  и при промахе: тихое «мимо» скрыло бы битые данные.

### 4. Кости в спеке урона необязательны

`damage: { bonus: '3' }` — урон оружия числом, без костей (Shadowrun).
`rollNotation` зовётся только при наличии `dice`; без него `rolls: []`,
`notation: null`, `base = bonus`.

## Тест-план

Очереди костей фиксированы, числа предвычислены: Арвен (бонус атаки 6) бьёт
лонгсвордом Мирру (КД 14); кость атаки 10 ⇒ бросок 16, превышение 2; кость
урона 5, Сила 3 ⇒ база 8.

1. Отчёт атаки несёт `check {success, margin, dice}`: при попадании
   `margin = 2`; при промахе `success: false`, `margin` отрицателен.
2. Натуральная кость видна: `check.dice.kept` — на очереди с двадцаткой.
3. Отчёт спасброска несёт ту же структуру (`margin = save.total − dc`).
4. Система **без** `rules` ⇒ поведение прежнее (`source: 'roll'`, урон = базе).
5. **Лакмус:** два `send` одной записи по одинаковой очереди костей; системы
   отличаются одной строкой (`source: 'margin'`) ⇒ урон 8 против 10.
   Движок между прогонами не менялся — импорт один.
6. Бескостевой урон: `{ bonus: '3' }` при `source: 'margin'` ⇒ урон 3 + 2 = 5 —
   пример из документа (меч 3, превышение 2).
7. Конверт остаётся чистыми данными: JSON round-trip побайтно.
8. Хиты получателя падают на **финальный** урон (с превышением), не на базу.
9. Неизвестный `source` — внятная ошибка в `send` и в `receive`.
