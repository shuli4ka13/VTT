# Переделка конструктора эффектов: понятность

Дата: 2026-08-11. Согласовано с Владом на макетах (сессия brainstorm, картинки в
`.superpowers/brainstorm/`). Статус: утверждено, фаза 1 — в работу.

## Проблема

Конструктор шагов (`apps/web/src/screens/constructor/`) непонятен целевому
автору-некодеру:

1. Палитра показывает пять команд движка («порог», «величина», «сравнение»,
   «применить», «состояние») — ассемблер вместо языка игры. Непонятно, из чего
   собирается атака и почему урон называется «величиной».
2. Экран нигде не произносит, что цепочка ДЕЛАЕТ — только «эффект верный».
3. Связь эффект ↔ род записи ↔ запись компендиума («у меча своя кость урона»)
   существует в модели, но не видна ни на одном экране, и способов связи два
   параллельных (прямая ссылка на свойство и параметры+привязка).
4. Заполнение слота требует сначала выбрать «вид ссылки» из мета-выпадашки —
   таксономия модели данных торчит в интерфейсе.

## Решение — четыре опоры

### 1. Пересказ (readback)

На каждой карточке шага — зелёная строка: что шаг делает, словами, собранными
из лейблов самой системы («Класс брони», не «КД» и не `ac`). Незаполненные
места — оранжевые пропуски («⟨какого поля цели?⟩»). Пересказ всего эффекта —
эти строки, прочитанные подряд. Жаргона нет: слова «дырка», «слот», «привязка»
в интерфейс не выходят.

### 2. Палитра: заготовки + три кирпича поверх пяти команд

Движок не меняется: пять типов шагов (`threshold/amount/compare/apply/status`)
остаются как есть. Склейка — только на экране:

- **Проверка** = `threshold` | `compare`, переключатель «броском / без броска»
  (умолчание — броском). Может оборвать цепочку; обрыв показан на карточке
  («промах — эффект кончается»).
- **Изменение** = `apply` | `status`, переключатель «поле / состояние».
- **Число** = `amount`, отдельной карточкой — только для редких случаев
  (превышение порога, одно число на несколько изменений).

Первый ряд палитры — заготовки на языке игры: «+ атака с броском», «+ просто
урон», «+ лечение», «+ наложить состояние». Заготовка кладёт собранную и
названную цепочку — работает сразу, автор меняет значения. Кирпичи — второй ряд.

Атака из заготовки — две карточки без имён шагов: «Изменение» умеет держать
«сколько: 1к8 + мод Силы» в себе. В данных это по-прежнему пара
`amount`+`apply` (движок и журнал не трогаем): UI рисует одной карточкой пару
«amount, на который ссылается ровно следующий apply», и правит оба шага.

### 3. Нить «Атака ← Оружие ← Меч» через три вкладки

Единственный способ связи эффекта с записью — через объявленные потребности
(нынешние params; в интерфейсе — «берёт из записи»). Прямая ссылка шага на
свойство записи (`prop` в слотах шагов) уходит.

- **Эффекты**: секция «Берёт из записи: кость урона» — на виду, не в свёртке.
- **Записи**: выбрал в привязке эффект — экран показывает его потребности и
  кнопкой предлагает «завести свойство „Кость урона“». Не закрыты все
  потребности — красный приговор со списком.
- **Компендиум**: форма записи из рода (как сейчас) плюс строка «владелец
  получит: Атака».

Требует правки модели и переписывания образцов; конвертация существующих миров:
прямая ссылка на свойство превращается в потребность + строку привязки.

### 4. Слот без таксономии

Вместо пары «вид ссылки» + «значение» — одно поле с подсказкой: пишешь число
или формулу, либо выбираешь из списка («поле цели…», «из записи…», «результат
шага…»). Вид определяется выбором человека, а не предварительной выпадашкой.

## Фазы

**Фаза 1 — прототип вкладки «Эффекты»** (ветка `rules-constructor`, старые
экраны живут до одобрения): пересказ, заготовки, три кирпича, склейка карточек,
слот без таксономии. Модель не трогается. Критерий: Влад собирает «Огненный
шар» без подсказок.

**Фаза 2 — нить** (детализация согласована 2026-08-12, фаза 1 сдана):

*Модель — одна связь.* Шаги эффекта ссылаются «из записи» ТОЛЬКО через
потребности (нынешние `params`); прямые `{prop}`/`{item}` в слотах шагов
запрещены. Привязка рода закрывает каждую потребность своим свойством
(`args[param] = {prop}`), константой или формулой. Движок не меняется:
обе формы он уже умеет, меняется, ЧТО пишут данные и экраны.

*Конвертация.* Чистая функция `unifyRecordRefs(system)`: каждый `{prop}` в
слоте шага → потребность (ключ = ключ свойства, если свободен; лейбл — из
объявившего рода) + слот `{param}` + строка `args` во всех родах, привязанных
к эффекту. Зовётся при загрузке стора, импорте мира и открытии
опубликованного. Образцы переписываются в данных сразу (руками, не
конвертером): «Атака» D&D объявляет потребность «кость урона», род «Оружие»
закрывает её свойством.

*Экран «Эффекты».* Секция «Что эффект берёт из записи» — видимая таблица
(название, чем заполнят, кто считает), не свёртка. В подсказке слота — пункт
«из записи → новая потребность»: создаёт её на месте и вставляет ссылку.
Остаточный `{prop}` в слоте — ошибка приговора с подсказкой перенести.

*Экран «Записи».* Привязка выбрала эффект — под ней его потребности списком;
каждая закрывается свойством рода (выпадашка) или значением; рядом с
незакрытой — кнопка «+ завести свойство „<название>“» (создаёт prop
подходящего вида и сразу закрывает потребность). Не закрыто — красный
приговор со списком.

*Компендиум.* Строка «владелец получит: <привязки рода>» в форме записи.

*Красные доноры.* `problemOf` возвращает, ЧЕГО не хватает (тег поля), а не
только текст; рядом с ошибкой «поля X нет» — кнопка «взять блок „Y“ из
<донора>», дёргающая существующий механизм блочных доноров (транзитивное
замыкание, топологический порядок). Для недостающего свойства — переход
на «Записи».

*Словари системы* (по решению 2026-08-12): в левой колонке «Эффектов», под
«Действуют на всех», фолд «Словари» с двумя секциями. «Кости»: константы
`kind:'die'` — завести (название + запись `1d20`), переименовать, удалить,
если не используется; составные кости (пары Daggerheart) — только показ.
«Мишени бросков»: самостоятельные мишени (`system.rolls`) — завести
(название → тег), удалить, если не используется; чек-мишени полей остаются
на «Листе». Методы преимущества — НЕ в этой фазе (решение Влада).

**Не в этой работе**: перестановка шагов, undo, стол и экран игрока,
отыгрыш остальных методов преимущества, старый vanilla-PoC (`src/` —
замороженный эталон, не трогать).

## Образцы — данные, не код (решение Влада, 2026-08-12)

Образцовые системы хранятся как `samples/*.world.json` — файлы формата мира,
который выгружает сам конструктор. Код (движок, сид, палитра доноров, тесты)
их только читает. Dogfood-критерий: **образец D&D воспроизводим конструктором
с нуля**; конечное состояние — файл образца это экспорт из конструктора, не
рукопись. Для этого словари фазы 2 включают редактор таблиц по диапазонам
и типы действий. Радикальный вариант «только в базе, без файлов» отклонён:
свежий чекаут, CI и пустой стенд обязаны воспроизводиться из репозитория.

### Чего ещё не хватает до dogfood (замерено финальным ревью 2026-08-12)

Середина образца D&D уже кликается целиком: поля и формулы, эффекты с
цепочками, потребности и их закрытие свойствами, рода и записи, правила
комнаты, кости, мишени бросков, таблицы по диапазонам, типы действий,
модификаторы значений и бросков с условиями. Не собирается пока:

- `advantage.methods` системы и выбор метода у roll-модификатора (`method`
  захардкожен `rerollBest`) — отложено решением Влада;
- `description` эффекта — поля нет в редакторе;
- свой `roll.label` у поля («Спасбросок Ловкости») — тумблер на «Листе»
  генерит только «Проверка: X» и лейбл не даёт править;
- `sheets` — конструктора чарников нет вовсе (отдельный экран, не эта фаза);
- киберпанк дальше: `source: {param}` у величины, дотированные ссылки
  (`{ref:'pen.margin'}`), `target: {param}` у изменения, собственные
  `activities` записи и args action-записи — редакторов нет.

Косметика, поведенчески эквивалентная: `trigger.when` по умолчанию, значки
(убраны сознательно), латинские ключи образца против кириллических от
`freeId` — движок ключи не хардкодит.


## Что НЕ эффект: словари системы (решение Влада, 2026-08-12)

Правило, по которому вещь попадает в словари, а не в библиотеку эффектов:

> **Нет вопроса «когда срабатывает» и одинаково для всего мира — это словарь
> системы, а не эффект.**

Эффект — единица автоматизации, и род у него задаётся тем, КОГДА он
срабатывает. Вещь, у которой такого вопроса нет, эффектом быть не может:
она ни на ком не висит, ничего не запускает, её нельзя снять. Попытка
сделать её эффектом даёт сущность-призрак и второй способ сказать то же
самое — ровно ту двойственность, ради устранения которой затевалась фаза 2.

Уже в словарях: кости (константы), мишени бросков, таблицы по диапазонам,
типы действий.

### Механики преимущества — разделить на две вещи

Сегодня они склеены, и отсюда путаница:

- **ПОВОД** — «во фланге атаки идут с преимуществом», «пока отравлен —
  помеха». Ситуативно, висит на персонаже, снимается. Это ЭФФЕКТ, и он
  уже так и сделан: пассивный + roll-модификатор + условие. Не трогать.
- **МЕХАНИКА** — «преимущество значит: два d20, берём лучший». Закон мира,
  один на систему: в 5e так всегда, в Savage Worlds это «кость ступенью
  выше», в Blades — «лишняя кость в пул». Это СЛОВАРЬ.

Чекбоксы из черновика тимлида (`reference/index.html`, `ADV_METHODS`) были
правы — они описывали механику, а не повод.

**Что делать (не сделано):**

1. Пятая секция во вкладке «Словари» — «Механики преимущества»: семь
   известных механик с примерами систем (`packages/engine/src/model/
   advantage-methods.ts`), галочка «есть в моём мире». Место в данных уже
   есть: `system.advantage.methods` (схема, `world.ts`).
2. Roll-модификатор эффекта говорит только «преимущество/помеха», а метод
   выбирает из ВКЛЮЧЁННЫХ в мире (если включён один — не спрашивать вовсе).
   Сейчас метод захардкожен в `modifiers.tsx:57` (`rerollBest`) — это
   единственная настоящая недоделка в связке.
3. Движок отыгрывает 1 механику из 7 (`dice.ts`, две кости — лучшая).
   Остальные добавляются по одной как трансформеры СТРУКТУРНОГО броска —
   не текстовой подстановкой в формулу: гашение помехой, нестакаемость
   и журнал этого не переживут (проговорено 2026-08-11).


### Как это решено у других (проверено 2026-08-12)

**Foundry + dnd5e — то же разделение.** Механика живёт в движке бросков
(модификаторы `adv`/`dis` в формуле: `3d6adv` — шесть кубов, лучшая тройка),
повод — в Active Effects, которые по документации ВСЕГДА привязаны к актёру
или предмету и общесистемных правил не задают. Источники сливаются:
преимущество от системы плюс помеха от флага модуля дают обычный бросок,
и оба источника показаны игроку — наше «помеха гасит преимущество» совпадает.

**Custom System Builder и Sandbox** (ближайшие аналоги: конструкторы систем
без кода) идут третьим путём — понятия «преимущество» у них НЕТ. Автор пишет
бросок формулой, и преимущество это просто `2d20kh1` в выражении.

**Почему нам не годится третий путь:** наши roll-модификаторы приходят от
ЭФФЕКТОВ, а эффект не знает, какой бросок поправит. «Фланг даёт преимущество»
— про любой бросок атаки любой костью; вписать туда `2d20kh1` нельзя (сломается
в системе на d100, и гасить помехой будет нечего). Именно поэтому Foundry
держит именованное понятие, а не голую формулу.

**Почему не как в Foundry:** у нас конструктор для некодера, механика обязана
быть данными — иначе Savage Worlds («кость ступенью выше») требует программиста.

**Чего не хватает по сравнению с CSB:** парсер костей понимает только `NdM`
(`packages/engine/src/engine/dice.ts`). Записать `2d20kh1` руками нельзя —
а это простой запасной выход, пока механика не отыграна. Стоит добавить
поддержку keep-highest/lowest в нотации: тогда автор не заперт словарём.


### Бросок как ЗАЯВКА через конвейер (идея Влада, 12.08; направление на следующий заход)

Влад предложил: не учить эффект механике, а «посылать бросок наверх — пусть там
решат, что с ним делать, и вернут». Это известный паттерн, и у больших он так
и сделан: в Foundry бросок сперва собирается объектом-конфигом (`parts`,
`advantageMode`), затем срабатывает хук `dnd5e.preRollAttackV2` — модули правят
конфиг или отменяют бросок, — и ТОЛЬКО потом он вычисляется.

**У нас есть половина этого шва.** `resolveRoll(system, sheet, rollTag, pass)`
(`packages/engine/src/engine/modifiers.ts`) спрашивает мир про бросок и
возвращает `{ mode, bonus, methods, sources }`; `rollLead` бросает. Но `mode`
имеет ОДНУ зашитую трактовку — две кости, лучшая (`dice.ts`).

**Куда это развивать:** пусть сбор возвращает не режим, а список ПРЕОБРАЗОВАНИЙ
заявки, и каждая из семи механик — модуль за реестром, как типы шагов:

    заявка: { костей, граней, оставить, прибавка, порог }
      переброс лучшего  → костей: 2, оставить: 'старшую'
      добавить кость    → костей: +1
      сдвиг сложности   → порог: −2
      рост кости        → граней: 20 → 30
    бросок
      сдвиг степени успеха — уже по результату

Ядро не знает ни одной механики лично; новая = модуль + строка в реестре
(тот же приём, что для `engine/steps/`). Это НЕ замена решению «механика —
словарь, повод — эффект», а его исполнение: словарь говорит, какие
преобразования есть в мире; эффект — когда они включаются; конвейер применяет.

**Перед кодом — исследование (Влад просил именно так):** разобрать броски
3–4 систем с непохожими механиками (Savage Worlds — ступень кости; Blades —
пул с добором; CoC 7e — бонусная кость десятков и уровни сложности; PbtA —
сдвиг степени успеха) и проверить, выдержит ли форма заявки их все, прежде
чем закреплять её в движке.


### Правки броска — свой словарь автора, а не семь чекбоксов (12.08, основное направление)

Влад: «задача не спиздить у Foundry, а сделать удобно». Верно, и это меняет
предложение. Foundry проверялась для ВНУТРЕННЕГО устройства (жив ли механизм
заявки) — снаружи у неё ответа нет вовсе: там это API для программиста,
ради чего наш проект и затевался.

**Наблюдение, из которого всё следует:** «преимущество» — ДОМЕННОЕ слово,
а механике мы их запретили (принцип 1). В 5e это «преимущество», где-то
«фора», «удача», «превосходство». Значит, называет его автор — как поле,
эффект и кость.

**Форма:** словарь «Правки броска», устроенный как словарь костей.

    ПРАВКИ БРОСКА
    [Преимущество]  кинуть на кость больше, оставить лучшую   гасится: Помехой
    [Помеха]        кинуть на кость больше, оставить худшую   гасится: Преимуществом
    [Вдохновение]   добавить кость к сумме

Слева имя автора, справа — что запись делает с ЗАЯВКОЙ броска, собранное из
горстки примитивов: добавить кость / оставить лучшую-худшую / сменить размер
кости / сдвинуть порог / сдвинуть степень успеха. Roll-модификатор эффекта
ссылается на запись фишкой: «на броски атаки — ⟦Преимущество⟧» — так же, как
слот ссылается на кость `[1d20]`.

**Что это даёт против чекбоксов:**
- автор не встречает слова «метод» и не выбирает из чужого списка — заводит своё;
- мир не заперт в паре «преимущество/помеха»: их может быть сколько нужно;
- «помеха гасит преимущество» перестаёт быть зашитым законом движка и
  становится строкой в словаре («гасится: …»); где они складываются — автор
  просто не заполнит это поле;
- семь механик черновика (`model/advantage-methods.ts`) превращаются не в
  чекбоксы, а в ГОТОВЫЕ ЗАПИСИ ИЗ ОБРАЗЦОВ — по принципу «у готового есть автор».

**Цена:** движок вместо `mode: 'advantage'|'disadvantage'` носит список
применённых записей и складывает их преобразования (`resolveRoll` → заявка →
`rollLead`). Половина шва есть, но это не работа на вечер. Гашение и
нестакаемость переезжают из кода в данные, значит нужны тесты на обе.

## Проверка успеха

- Сборка атаки из заготовки — две карточки, ноль имён шагов, ноль слов
  «слот/дырка/привязка» на экране.
- Пересказ собирается из лейблов системы; переименование лейбла меняет пересказ
  и не ломает ничего (критерий приёмки №2 проекта).
- Старые миры открываются: фаза 1 не меняет данные вовсе, фаза 2 конвертирует.
