# Бросок двух полей и порог, названный перед броском

Статус: черновик 1 (13.11), советнику не показан. Повод — Fabula Ultima (`docs/fabula-ultima.md`): каждая проверка —
две кости двух характеристик, сложность называет ведущий. Сейчас с листа такую проверку не бросить вовсе.

## Что проверено до плана (13.11)

Три «дыры движка» из `roll-meaning.md` («Что мешает перевести образцы») оказались не дырами — собираются данными:

- Daggerheart: черта оружия → поле листа через клетку справочника и адрес с вычисленным именем
  `@действующий.[@trait.field]` (`run.ts: addressName`); проба дала те же числа.
- Cyberpunk: одна правка на любую из меток — `anyTags` (`modifiers.ts: tagsFit`), двойного счёта нет.
- Blades: рейтинг — поле листа, в эффект приходит входом-ссылкой (`run.ts: fieldOf`, вход вида `field`).
- Встречная по степеням (Imperium Maledictum) — два броска поля и «Проверка», `field-roll-step.md` §5.

- Fabula Ultima кнопкой (13.11, `samples/fabula.lite.world.json`, `tests/samples.fabula.test.ts`): характеристика — клетка-кость
  листа, проверка — два шага «Бросок» с костью `@действующий.[@первая.поле]` и «Проверка» суммы против сложности,
  которую спрашивают у ведущего; атака — те же две кости до цикла, урон — старшая кость плюс число оружия. Играется.
  Цена: автоуспех дубля и автопровал единиц записаны формулой порога (в журнале «порог: 0» / «порог: 999»), и
  «Проблемы» честно замечают, что правки цели на сумму двух бросков не действуют.

Правка движка ниже нужна только затем, чтобы то же бросалось **щелчком по полю листа**. Она отменяет два принятых
решения `roll-meaning.md` §1 («слота сложности нет», «несколько бросков вместе — всегда „Проверка“»), поэтому
не начата: ждёт решения владельца. Поправки советника к черновику: условие «не считать формулу успеха» сузить до
формул, читающих `@порог` без порога; ключ второго поля не `with` (слово JS); добавить конструктор (галочка «два поля»
у правила, второе поле в карточке «Бросок»); тест пересчёта «против» для двух граней.

## Чего не хватает

1. **Размер кости — число поля** уже есть (`number: 'sides'`), но только для кости из одного вида
   (`dice.ts: withSides` отказывает составной).
2. **Два поля в одном броске.** Операция `roll` и шаг «Бросок» принимают одно поле.
3. **Порог извне для правила без своего порога.** `throwField` считает успех и степени, только если порог знает
   правило (число поля «не больше / не меньше», порог записи). Назвать его перед броском нельзя.

## Решение

### 1. Правило: кость из двух частей, грани каждой — своё поле

Кость правила — константа из двух видов с частями (как `duality` Daggerheart): `[{count:1, sides:6, part:'первая'},
{count:1, sides:6, part:'вторая'}]`, у правила `number: 'sides'`. Новое в данных правила одно:
`pair: true` — «бросают два поля». Без него всё как сейчас.

- `withSides(spec, sides: number | number[])`: список — по одному числу на вид, длины обязаны совпасть.
- `Check` получает `sides2` (формула второго поля). `fieldCheck(system, tag, tag2?)`: при `pair` второе поле обязано
  стоять в том же правиле; не задано — берётся то же поле (книга: одна характеристика — кость бросается дважды).
- Итоги — как у любого броска с частями: `.total`, `.parts.первая`, `.parts.вторая`, `.dice.rolls`. «Старшая кость»
  урона — `большее из(@бросок.parts.первая, @бросок.parts.вторая)`, нового пути не нужно.

### 2. Откуда второе поле

- **Шаг «Бросок»:** `field` + `with` (адрес второго поля, тот же разбор `fieldOf`; лист в голове обязан совпасть с
  первым — иначе отказ «бросают один лист»). Линт: `with` без `pair` у правила — ошибка; `pair` без `with` — норма.
- **Операция стола:** `{ op: 'roll', sheetId, tag, with?: tag }`.
- **Экран листа:** у правила с `pair` рядом со словами перед броском — выбор «вторая характеристика» из полей того
  же правила, по умолчанию «та же». Одно понятие — один выбор на лист, не у каждой кнопки.

### 3. Порог, названный перед броском

- **Операция стола:** `{ op: 'roll', …, versus?: number }`. Экран: необязательное число «сложность» рядом со словами.
  Показывается только у правил без своего порога (у «не больше» сложность — слова со сдвигом, как в Вахе).
- **`throwField`:** своего порога нет, а `versus` пришёл — он и есть порог: к нему прибавляются те же сдвиги
  (`shiftVersus`, правки «Бросок → порог»), успех по умолчанию `выпало >= порог`, степени `выпало − порог`.
- **Формулы правила «Успех, если» и «Степени»** считаются, только когда порог известен. Сейчас у правил без порога
  их нет ни в одном образце, так что поведение образцов не меняется. Без `versus` бросок — как сейчас: число.
- **Ступени списком** считаются всегда (как сейчас) и видят `успех`/`степени`, только когда те есть: «критический
  успех» Fabula (дубль от 6) — ступень, видимая и без сложности.
- **В эффекте ничего нового:** там порог знает эффект — «Проверка» против числа (`roll-meaning.md` §1 остаётся).
  `versus` у шага не заводится.

Это отменяет строку `roll-meaning.md` §1 «отдельного слота «Сложность» нет» только для щелчка по листу: на листе
«Проверки» нет, и сравнить иначе нечем.

### 4. Чего не делаем

- Состояния, понижающие размер кости на ступень; перебросы за очки Фабулы «одна или обе»; Связь; групповая проверка —
  в `fabula-ultima.md` «Где модель не дотягивает» п. 2, 4–6. Лёгкий мир — без них.
- Запрос броска ведущим у игрока.
- Правка граней кости правкой броска.

## Образец

`samples/fabula.lite.world.json` — только то, что есть в выписке: характеристики-кости, проверка против сложности,
атака (меткость против защиты, урон — старшая кость + число оружия), лекарство без броска. Чего в выписке нет
(формулы ОЗ/ОМ, защита от характеристик, списки оружия) — поля вводятся числом, записи берутся только названные
в выписке.

## Риски

- `Check` и `fieldRollOf` читают многие места (`toggles.ts`, `names-at.ts`, линт): `pair` — необязательный ключ,
  без него путь прежний.
- Журнал комнаты (`room_journal`) хранит намерение: новые ключи `with`/`versus` — часть намерения, переигровка по
  журналу обязана совпасть (`test/journal.test.ts`).
- Экран: две новые вещи в строке «заявить к броску с листа» — не превратить её в простыню; обе показываются
  только когда система их требует.
