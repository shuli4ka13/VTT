# Один способ собрать бросок во всех системах: смысл броска — в правиле, сложность — из шага

Статус: предложено, ждёт проверки советником. Не реализовано.

## Зачем

Владелец 11.11: «не хочется, чтобы броски в разных системах собирались по-разному»; «где вводить степени,
названия степеней, исходы — как будто надо и так и так».

Сейчас одно понятие «что значит этот бросок» живёт в двух местах с двумя редакторами:

- **правило броска** («Правила → Броски», `system.rolls`): «Успех, если», «Степени числом», «Ступени» (список
  `{ label, if }`). Видно на экране только при пороге или если уже заполнено (`rolls-section.tsx`), иначе подпись
  «успеха и степеней правило не считает — их решает «Проверка» в эффекте»;
- **«Проверка» в эффекте** (шаг `check`): `value`, `versus`, `successWhen`, `succeedOn`/`failOn`, `degrees` —
  ссылка на таблицу (`{ table: 'outcome' }`, Blades).

Опись образцов 11.11: шагов «Бросок» 77, по правилу из «Бросков» (бросок поля) — 2, оба D&D, оба этой недели.
Остальные — кость + прибавка формулой, смысл — в «Проверке» после. Ступени у проверок — только Blades (2).
Причина в основном — возраст: бросок поля появился 09.11 (`field-roll-step.md`), образцы последний раз правились
03–07.11. Но три места правило выразить не может — они ниже, в «Чего не хватает».

## Решение

### 1. Два уровня, одно понятие

- **Правило броска** — смысл **одного** броска поля: кость, что такое число поля, против чего (порог), успех,
  степени, ступени. Всё, что следует из самого броска и его сложности.
- **«Проверка» в эффекте** — смысл **нескольких** бросков вместе: встречная (сравнить степени двух бросков),
  сложение двух бросков (Fabula Ultima — по памяти, см. «Открыто»), бросок без правила (урон, таблица случайностей).
- **Ступени** — один редактор в обоих местах, два вида данных, оба допустимы и там, и там: список `{ label, if }`
  (первая подходящая сверху; так у правила сейчас) и таблица-промежутки `{ table, of: 'margin' | total }`
  (`tables.ts: lookupDegree` — строка по числу, сдвиг ступени правками `degreeShift`; так у «Проверки» сейчас,
  Blades `outcome`).

Проверка системы = шаг «Бросок» с полем (или с числом по правилу, п.3). У шага всегда есть итоги правила:
пройден, степени, ступень — если правило их считает.

### 2. Против чего — у правила, сложность — из шага

У правила «Число поля — это» решает, что делает число поля; новое — откуда порог, если число поля им не
является:

| Порог | Пример | Данные |
|---|---|---|
| нет порога | урон, инициатива | как сейчас |
| число поля («не больше / не меньше») | Warhammer, Call of Cthulhu | `number: under / over`, как сейчас |
| формула от листа | Shadowrun «Прыжок» | `threshold: { expr }`, как сейчас |
| **из шага** | D&D против КД / сложности, Daggerheart против сложности, Cyberpunk против СЛ | `threshold: 'step'` (новое) |

- **Порог решается у поля**, как сейчас у «Прыжка»: `threshold` правила — умолчание для его полей, поле может
  задать своё. Порог поля (формула от листа) сильнее: сложность шага при нём — ошибка линта «у поля свой порог».
- **Направление** — существующий признак `under` правила: без него «выпало не меньше порога», с ним — «не больше».
  У «из шага» он значит то же.
- **Шаг «Бросок»** с таким полем — слот «Сложность» (`difficulty: { expr }`), виден только у таких полей; формула
  считается в области эффекта (`@цель.кд`, `@сложность`). Нет сложности у шага — ошибка линта.
- **Щелчок по полю на листе** — шага нет, сложности нет: успех не считается, бросок складывается (как сейчас
  у правила без порога), ступени, которым нужен порог, не выбираются.
- Сложность шага становится `base` в `throwField` — на неё действуют правки порога и сдвиг «против», как на порог
  поля. Поправка к числу поля (`shift`) остаётся как есть.

Механизма «сложность из следующей «Проверки»» нет: `Run.ahead` ищет только **соперника** для правок «против»
(`roll-against.md` §1), а не число. Слот явный — его видно и правят на месте.

### 3. Бросок по правилу без поля

Пул из входа или вычисленный (Shadowrun: оружие отдаёт `attack_pool = @skill.pool`) — либо адрес поля через
вход-выбор (`@действующий.attack_skill.pool` — уже работает), либо шаг «Бросок» по правилу с числом формулой:
`{ rule: 'проверка', number: { expr } }` — правило целиком, бросающий — `by`. Тогда **любая** проверка —
«правило + число + сложность»; поле — частый источник числа, не единственный.

### 4. Чего не хватает в именах правила

Сейчас формулы правила видят `выпало` (итог с прибавками), `число`, `порог`, `успех`, `степени`
(`core/run.ts: throwField`). Для систем нужны ещё натуральная кость, грани, части, сколько легло максимумом и
единицей, сколько бросили — то, что «Что отдаёт» перечисляет у любого броска.

Новых имён не заводится — у этих величин уже есть пути у шага (`@шаг.natural`, `.parts.надежда`, `.dice.rolls`,
`.atMax`, `.atMin`, `.rolled`) и подписи в «Что отдаёт». В правиле этот же бросок зовётся **`@бросок`**, и пути
те же: `@бросок.natural == 20`, `сколько(@бросок.dice.rolls, 6) >= 2`, `@бросок.atMin * 2 > @бросок.rolled`,
`@бросок.parts.надежда > @бросок.parts.страх`. Одно понятие — один путь в обоих местах; подсказка после
`@бросок.` — тот же список «Что отдаёт» (`names-at.ts: resultsOf`). `бросок` — в занятых именах правила
(`lint.ts`, рядом с `выпало` и `число`).

| Путь | Кому |
|---|---|
| `@бросок.natural` | D&D крит на 20 |
| `@бросок.dice.rolls` | Blades «две шестёрки» |
| `@бросок.atMin`, `@бросок.rolled` | Shadowrun сбой «больше половины единиц» |
| `@бросок.parts.<часть>` | Daggerheart «с надеждой / со страхом», крит на равенстве |

### 5. Экран

- Правило: «Успех, если», «Степени числом», «Ступени» видны всегда; пусто — подсказка «пусто — не считается».
  Подпись «правило не считает — решает «Проверка»» уходит. «Порог» — строка «Против чего» с пунктами таблицы п.2.
- «Что приходит» показывает `@бросок` с его путями и `порог` только когда он есть.
- Шаг «Бросок» с полем порога «из шага» — строка «Сложность».
- Ступени — один компонент (`degrees-editor`) в правиле и в «Проверке».

## Встречная и ничья (Warhammer)

Отдельной строки «При равенстве» не нужно. Правило книги (`docs/imperium-maledictum.md` на ветке
`claude/amazing-pike-5feb34`, §3, с. 190): выигрывает больший SL; итоговый SL = свой − чужой; при равенстве SL —
больший навык, дальше решает ведущий. Это итоги и ступени «Проверки» нескольких бросков тем же редактором:
«победил» = больше степеней, равно → больший навык; ступень «решает ведущий» — равны и степени, и навык.

## Порядок относительно `dice-by-step.md`

Сначала эта модель, потом снятие «кинуть»: образцы переписываются один раз — проверки становятся бросками по
правилу, урон — шагом «Бросок» с костью. Таблица образцов `dice-by-step.md` вливается в план образцов здесь.

## Что заменяет

- `field-roll-step.md` §1 «кто бросает — голова адреса» (дополняется п.3: бросок по правилу без поля с `by`).
- Подпись и условие показа в `rolls-section.md` / `rolls-section.tsx`.
- `roll-step-cards.md` п.6 «формула вокруг броска в «Проверке» остаётся» — для одного броска с правилом это
  больше не путь; остаётся для бросков без правила.

## Порядок работ

1. Движок: имена п.4 в формулах правила; порог «из шага» и слот «Сложность»; бросок по правилу с числом (п.3);
   ступени таблицей у правила. Линты. (я — ядро)
2. Экран: правило — строки всегда, «Против чего»; шаг — «Сложность»; один редактор ступеней. (`executor`)
3. Образцы: проверки на правила по таблице выше, вместе с `dice-by-step.md`. (`executor` по таблице)
4. Прогоны (скилл `checks`), ревьюер — дифф ядра.
